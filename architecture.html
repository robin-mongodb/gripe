Gripe — Architecture

One EC2 host running the app via docker-compose. RDS PostgreSQL and MongoDB Atlas are managed. SQS fans out to two mock async workers to mix reads+updates against both DBs.
or Atlas, one at a time via config flag) ④ api publishes {payment_id, ...} to SQS ⑤ fee-worker consumes payment.created and does one set-once conditional update (fraud-worker is an idle stub — parked) ⑥ workers hit whichever DB is configured — dashed lines show both options; only one is live at once
EC2 (docker-compose) SQS RDS PostgreSQL MongoDB Atlas

Why this shape

  • Config flag picks Mongo or PG at boot — same code, one backend live at a time. Perf comparison runs the same scenario twice.
  • Workers are separate processes so the DB sees mixed load (read + update per payment), not just inserts.
  • SQS is backend-agnostic — both DBs get the same event pattern. Change Streams / LISTEN/NOTIFY are parked for the live-event-feed UI, not for worker triggering.
  • EC2 + compose over ECS/Fargate for v1: one host, one deploy, cheapest. Lift-and-shift to Fargate later without code changes.
  • Perf outcome (2026-08-19): both backends held 368 req/s with zero errors; after tuning, Mongo won the tails (create p95 26 ms vs 69 ms), PG the read p50 (in-VPC path). See docs/perf-report.html, docs/data-models.html, docs/claude-dx.md.

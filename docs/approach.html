Where it landed (2026-08-19) — outcome vs this plan

  • Shipped as "Gripe" — a payments processing engine (create/capture/refund/settle, subscriptions, per-currency balances, idempotency), not the Control Centre. All 76 tasks done; the demo script passes identically on both backends.
  • AI scope (decisions 1–3) was parked, not built: no AI chat, no vector/fuzzy search, fraud-worker is an idle stub. The DB comparison differentiator became idiomatic data modeling instead — Mongo embeds refunds + balance maps (single-doc atomic money moves); PG is fully normalized with FKs (docs/data-models.html).
  • Deferred decisions resolved: perf tool = k6 (#10); seed = 50 merchants × 2,000 payments (#11). PG runs on an RDS Multi-AZ DB cluster (3× db.m6gd.large ≈ Atlas M30), not the M50-equivalent tuning box; Atlas auth moved to IAM (MONGODB-AWS).
  • Perf outcome: both backends held 368 req/s for 10 min, zero errors. After tuning (covered list index, onboarding cache, pool 200) Mongo won tail latency — create p95 26 ms vs 69 ms; PG kept the read p50 edge (in-VPC path). Report: docs/perf-report.html; DX note: docs/claude-dx.md.

2. Repo & code-sharing shape

One repo. One frontend. One REST contract. One perf harness. A single Store interface has two implementations behind it.

  • The interface is use-case shaped, not CRUD shaped — so each impl can be idiomatic.
  • Each impl is free to use its DB's strengths (aggregation pipelines / Atlas Search / Change Streams on one side; CTEs / tsvector / pgvector / LISTEN/NOTIFY on the other).
  • A single contract-test suite runs against both via testcontainers — parity is enforced, not hoped for.

Interface sketch

type Store interface {
    SearchPayments(ctx, query, filters) ([]Payment, error)      // fuzzy + filter
    FindSimilarPayments(ctx, vec, k, filters) ([]Payment, error) // vector kNN
    GetPaymentTimeline(ctx, customerID, window) (Timeline, error) // fraud context
    SubscribeToPaymentEvents(ctx) (<-chan Event, error)          // live feed
    // ... plus CRUD-shaped ops for create/get/update
}

No Find(collection, filter) or Query(sql, args). The interface hides how.

5. Performance testing — planning notes

  • Design scenarios around the chains a support worker actually runs: search partial customer ref → open payment → fetch similar cases → ask the agent → post note.
  • KPIs: p50/p95/p99 latency, throughput, error rate. Track per endpoint and per full user flow.
  • Parameterize payloads with realistic distributions (Zipfian for customer IDs so caches actually matter).
  • Volume decided after the app is built — big enough that index choices materially matter on an M50-equivalent.

6. Verification — what "done" looks like

Same demo script runs identically on both backends:

  1. make seed BACKEND=mongo|postgres populates the chosen store.
  2. Support worker opens control centre → fuzzy-searches a partial customer ref → gets ranked matches.
  3. Opens a failed payment → "similar cases" panel shows vector-nearest historical failures.
  4. Fraud panel shows the agentic model's decision + reasoning.
  5. Chat: "why did this fail?" — agent retrieves context via Vector Search / pgvector and answers.
  6. Live event feed shows a newly-landing payment without a page refresh.
  7. Perf run: HTTP load exercises the key chain; report shows p50/p95/p99, error rate, throughput for both DBs on the same scenario.

All 7 pass on both backends → v1 is done.

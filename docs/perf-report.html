Read this before quoting numbers

  • Network paths differ: RDS is reached in-VPC (~1 ms TCP RTT); Atlas via its public endpoint (~2.5–3.5 ms), both inside AWS eu-west-2. Roughly the entire remaining list-read gap (~1 ms p50) is this hop, not the database. A private endpoint would close it.
  • Durability parity: Mongo writes use w:majority; the RDS Multi-AZ cluster commits semi-synchronously to 1 of 2 standbys — comparable 2-of-3 semantics.
  • Read parity: both PG DSNs point at the writer (no reader-endpoint offload), matching Mongo primary reads.
  • Storage: PG on gp3 at the 3,000-IOPS baseline; neither run was IOPS-bound.
  • The pre-tuning Mongo collapse was code, not hardware: 3 writes per create (payment + 2 onboarding upserts), a list sort not fully covered by an index, and a 100-connection driver pool. Fixed, the same M30 absorbs 4× with headroom.
  • PG got the same fixes where applicable (onboarding cache), worth ~1.5 ms on create p50 — the comparison stayed apples-to-apples.
  • Load: create 160/s, list 160/s, refund-flow 40/s (2 requests each), subscription churn 8/s at 4×. k6 constant-arrival-rate from a separate loadgen EC2 instance; nginx bypassed.
